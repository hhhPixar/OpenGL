# 📖 OpenGL 引擎项目阅读指南

> 本指南面向**只有一点点 C++ 基础**的读者。
> 目标:带你从"看不懂任何一行"到"能独立改出一个带新功能的小程序"。
>
> 这个项目是一个仿 [Hazel](https://github.com/TheCherno/Hazel) / TheCherno OpenGL 系列教程的**分层式渲染引擎学习项目**。它不是一个完整游戏,而是一个**引擎骨架 + 两个示例客户端**,把游戏引擎最核心的几件事(窗口、事件、分层、渲染、调试 UI)拆成了清晰可读的模块。

读完这个项目,你会理解下面这些"看起来很高大上"的东西其实没那么神秘:

- 🏗️ **分层架构**:游戏引擎怎么用 Layer 把渲染、UI、逻辑解耦
- 🧩 **面向对象 & 多态**:`virtual`、`override`、抽象基类、接口
- 🧠 **现代 C++**:智能指针(`unique_ptr`)、`std::bind`、lambda、模板、宏、单例
- 📨 **事件系统**:键盘/鼠标事件是怎么从底层一路传到你写的代码里的
- 🎨 **OpenGL 渲染管线**:VAO/VBO/IBO、着色器编译、uniform、画三角形
- 🖱️ **Dear ImGui**:怎么做调试面板
- 🔧 **构建系统**:premake5 是怎么把一堆子项目组织起来的

## 1. 先跑起来(环境准备)

在读懂之前,先让它在你电脑上能编译运行,边读边对照。

```bash
# 1. 克隆(如果还没克隆)
git clone <这个仓库>
cd OpenGL

# 2. 拉取第三方依赖(GLFW/spdlog/glm/imgui 都是 git 子模块)
git submodule update --init --recursive

# 3. 生成工程文件(需要 premake5,见 scripts/ 或自己装)
#    Windows:双击运行 scripts/Win-Premake.bat
#    macOS/Linux:在仓库根目录运行
premake5 gmake2          # 生成 Makefile
#   或 premake5 vs2022   # 生成 Visual Studio 工程
#   或 premake5 xcode4   # 生成 Xcode 工程

# 4. 编译运行 OpenGL-Examples(或 OpenGL-Sandbox)
```

> ⚠️ 注意:顶层 `premake5.lua` 定义了**两个 workspace**——`OpenGL-Sandbox` 和 `OpenGL-Examples`。你想跑哪个示例,就用哪个 workspace 的 startproject。两个客户端共用同一个引擎库 `OpenGL-Core`。

编译成功后运行,你会看到一个深灰色窗口,里面画了一个可变颜色的矩形,旁边有 ImGui 调色板,能用鼠标/键盘移动相机。**这就是 ExampleLayer 干的事**——读到最后你会发现,这个看似简单的窗口背后,每一层都对应引擎里的一个模块。

   └────────┬────────┘               │  OnUpdate        │

## 4. 建议阅读顺序(最重要的一节)

不要从头到尾顺着目录读,那样会很挫败。按下面这条**由浅入深、先见森林再见树木**的路径读:

### 第 0 站:看一眼它怎么跑起来的
**文件:`OpenGL-Examples/src/ExampleApp.cpp`(只有 19 行)**

这是整个项目最短的文件,信息密度极高:
```cpp
class Example : public Application {            // 继承引擎的应用基类
public:
    Example() : Application("OpenGL Examples")  // 构造时给窗口起名
    { PushLayer(new ExampleLayer()); }          // 把自己的层塞进去
};
int main() {
    std::unique_ptr<Example> app = std::make_unique<Example>();
    app->Run();                                  // 进主循环
}
```
读完你就懂了:**"用这个引擎做一个应用"=继承 Application + PushLayer 一个自定义层 + main 里 Run**。整个引擎的存在,就是为了让这 3 行变得有意义。

### 第 1 站:应用基类 Application
**文件:`OpenGL-Core/src/GLCore/Core/Application.h` 和 `Application.cpp`**

这是引擎的心脏。重点看三件事:
- **单例**:静态 `s_Instance` + 静态 `Get()`。全程序只有一个 Application。
- **构造函数**:初始化日志 → 创建窗口 → 把 `OnEvent` 绑定成窗口回调 → 创建 ImGui 层并作为 overlay 压栈。
- **`Run()`**:主循环。看懂它,你就懂了一帧是怎么转的(见[第 5 节](#5-一帧的生命周期主循环))。
- **`OnEvent()`**:事件来了怎么分发(见[第 6 节](#6-事件是怎么流动的))。

### 第 2 站:层 Layer / 层栈 LayerStack
**文件:`OpenGL-Core/src/GLCore/Core/Layer.h`、`LayerStack.h`、`LayerStack.cpp`**

`Layer` 是一个**抽象基类**,定义了 5 个虚函数回调:`OnAttach`/`OnDetach`/`OnUpdate`/`OnImGuiRender`/`OnEvent`。`LayerStack` 用一个 `vector<Layer*>` 管理"普通层"和"overlay"两类。看懂这个,你就知道 `ExampleLayer` 重写的那些方法是谁在什么时候调用的。

### 第 3 站:事件系统(本项目的"高光时刻")
**文件:`OpenGL-Core/src/GLCore/Events/Event.h` 先读,然后 `ApplicationEvent.h`、`KeyEvent.h`、`MouseEvent.h`**

事件系统是整个项目最精巧的部分。重点理解:
- `EventType` 枚举所有事件类型;`EventCategory` 用**位标志**给事件分类。
- `EVENT_CLASS_TYPE` / `EVENT_CLASS_CATEGORY` 这两个**宏**帮子类省掉重复代码(看不懂宏没关系,文件里有详细注释)。
- `EventDispatcher::Dispatch<T>(func)` 是一个**模板函数**:运行时判断"这个事件是不是 T 类型",是的话就把它 cast 成 T 传给你的回调。这是整个事件系统的核心魔法。

### 第 4 站:窗口与平台抽象
**文件:`GLCore/Core/Window.h` → `Platform/Windows/WindowsWindow.cpp` → `Core/Input.h` → `Platform/Windows/WindowsInput.cpp`**

先看抽象接口 `Window.h`/`Input.h`,再看 GLFW 的具体实现。重点看 `WindowsWindow.cpp` 里那一堆 `glfwSetXxxCallback`:它们是**事件真正的发源地**——GLFW 检测到按键/鼠标,调用这些回调,回调里构造对应的 `Event` 对象,再交给 `EventCallback`(也就是 `Application::OnEvent`)。

### 第 5 站:ImGui 集成
**文件:`OpenGL-Core/src/GLCore/ImGui/ImGuiLayer.cpp`**

`ImGuiLayer` 是引擎和 Dear ImGui 的胶水。`Begin()`/`End()` 之间,每个层的 `OnImGuiRender()` 画出自己的调试面板。理解它就理解了"调试窗口是怎么叠在画面上的"。

### 第 6 站:工具模块
**文件:`OpenGL-Core/src/GLCore/Util/` 下的 `Shader.*`、`OrthographicCamera*.h/.cpp`、`OpenGLDebug.*`**

- `Shader.cpp`:怎么从两个 `.glsl` 文本文件编译出一个 OpenGL 程序(顶点着色器 + 片元着色器 → 链接成 program)。
- `OrthographicCamera` + `OrthographicCameraController`:正交相机(2D 常用),以及用 WASD/鼠标控制它的控制器。
- `OpenGLDebug`:打开 OpenGL 的调试输出,出错时自动打印。

### 第 7 站:回到客户端,把渲染管线串起来
**文件:`OpenGL-Examples/src/ExampleLayer.cpp` + `assets/shaders/*.glsl`**

现在所有零件都见过了,`ExampleLayer` 把它们拼成完整的渲染流程:
- `OnAttach`:创建 VAO/VBO/IBO、加载着色器(**分配资源**)
- `OnUpdate`:清屏、设 uniform、`glDrawElements` 画图(**每帧重画**)
- `OnEvent`:把事件交给相机控制器,再处理鼠标换色
- `OnImGuiRender`:画颜色调色板
- `OnDetach`:`glDelete` 释放资源(**RAII 的手动版**)

### 第 8 站:构建脚本
**文件:`premake5.lua`(顶层)+ 各子目录的 `premake5.lua`**

理解 premake 怎么把 `OpenGL-Core`(静态库)、第三方依赖(GLFW/Glad/ImGui)、客户端(可执行文件)组织到一起。这是工程化的重要一环。

## 5. 一帧的生命周期(主循环)

打开 `Application::Run()`,下面是每一帧发生的事(假设 60 帧/秒,每帧约 16ms):

```
while (m_Running) {                              ← 主循环开始
    ① float time = (float)glfwGetTime();          ← 取当前总时间(秒)
       Timestep ts = time - m_LastFrameTime;      ← 算这帧花了多久
       m_LastFrameTime = time;                    ← 记下来给下帧用

    ② for (layer : m_LayerStack)                  ← 依次更新每层逻辑
           layer->OnUpdate(ts);                   ← 比如 ExampleLayer 在这里画图

    ③ m_ImGuiLayer->Begin();                      ← 开始 ImGui 这一帧
       for (layer : m_LayerStack)                 ← 每层画自己的调试 UI
           layer->OnImGuiRender();
       m_ImGuiLayer->End();                       ← 提交 ImGui 渲染

    ④ m_Window->OnUpdate();                       ← 交换前后缓冲(把画好的显示出来)
}                                                 ← 下一帧...
```

**为什么用 `Timestep`?** 游戏逻辑应该"按时间推进"而不是"按帧推进"——不同电脑帧率不同,如果用"每帧移动 1 像素",快电脑就跑得飞快。乘以 `Timestep`(秒)后,移动速度就和帧率解耦了。

**循环什么时候停?** 当收到 `WindowCloseEvent`(点窗口的×),`OnWindowClose` 把 `m_Running` 置为 `false`,下一帧条件不满足就退出。

## 6. 事件是怎么流动的

事件的完整旅程,从你按下键盘到你的代码处理它:

```
你按下键盘
    │
    ▼
GLFW 检测到按键(GLFW 是窗口库,负责和操作系统打交道)
    │  调用你在 WindowsWindow.cpp 里用 glfwSetKeyCallback 注册的 C 回调
    ▼
WindowsWindow 的回调函数  (key_callback)
    │  把按键信息打包成一个 KeyPressedEvent 对象
    │  通过 m_Data.EventCallback(就是 Application::OnEvent)发出去
    ▼
Application::OnEvent(e)
    │  ① 用 EventDispatcher 派发:如果是 WindowClose 就处理掉
    │  ② 从层栈【顶到底】逆序遍历,把事件 e 交给每层的 OnEvent
    │     某层返回 Handled=true 就 break,后面的层收不到
    ▼
ExampleLayer::OnEvent(e)
    │  ① 先交给 m_CameraController.OnEvent(它可能要处理滚轮)
    │  ② 再用 EventDispatcher::Dispatch<MouseButtonPressedEvent>(lambda)
    │     匹配到鼠标按下事件就执行 lambda(换颜色)
    ▼
处理完毕
```

两个关键设计点:

1. **事件是"阻塞式"的**:事件一发生就立刻处理,不会先存起来。文件头注释里提到,未来可以改成"事件总线"缓冲起来,在帧的固定阶段统一处理(更接近商业引擎的做法)。

2. **从层栈顶到底传播、Handled 即停**:越靠后的层(overlay,比如 ImGui)优先收到事件。这保证了 UI 能"吃掉"事件不传给游戏逻辑——比如点在 ImGui 面板上的鼠标,不该同时被下面的游戏世界当成点击。(项目有个 commit 专门让 ImGuiLayer 拦截鼠标按下,就是这个意思。)

## 7. 层(Layer)与层栈(LayerStack)

`Layer` 是引擎解耦的核心抽象。一个层代表"一类需要每帧更新、可能收事件、可能画 UI 的工作单元"。比如一个游戏里:`BackgroundLayer`(画背景)、`GameplayLayer`(游戏逻辑)、`UILayer`(菜单)、`DebugLayer`(调试面板,通常是 overlay)。

```
LayerStack 内部用一个 vector<Layer*>:
┌────────────────────────────────────────────────────────┐
│ [Layer0] [Layer1] [Layer2] ... │ [Overlay0] [ImGuiLayer] │
│  ← 普通层,先入先出               │  ← overlay,后入先出      │
│  (m_LayerInsertIndex 指向分界)                                   │
└────────────────────────────────────────────────────────┘
        begin()                                       end()
```

- `PushLayer` 加到分界处(普通层区往后挤)。
- `PushOverlay` 加到最末尾(overlay 区)。
- 遍历(`begin()`/`end()`)按顺序,所以 **overlay 总在普通层之后更新/渲染**,意味着 overlay 画在普通层之上、且优先收到事件。

`Layer` 的 5 个回调各自被谁调用:

| 回调 | 谁调用 | 典型用途 |
|---|---|---|
| `OnAttach` | 被 push 进栈时 | 分配资源(创建 VAO、加载着色器) |
| `OnDetach` | 被移除时 | 释放资源(glDelete) |
| `OnUpdate(ts)` | 主循环每帧 | 游戏逻辑、渲染 |
| `OnImGuiRender` | 主循环每帧(ImGui Begin/End 之间) | 画调试面板 |
| `OnEvent(e)` | `Application::OnEvent` 传播事件时 | 处理输入 |

## 8. C++ 知识点速查表

项目里反复出现的 C++ 特性,看不懂时回来查:

| 特性 | 一句话解释 | 在哪看到 |
|---|---|---|
| `virtual` / `override` | `virtual` 声明可被子类重写的函数;`override` 显式表示"我在重写父类" | `Layer.h`、`Window.h` |
| 纯虚函数 `= 0` | 抽象方法,子类必须实现,父类不能实例化(= 接口) | `Input.h`、`Event::GetEventType` |
| 多态 | 父类指针调用到子类重写的方法(运行期决定) | `Application` 持有 `Window*` 实际是 `WindowsWindow` |
| `std::unique_ptr` | 智能指针,独占资源,析构自动 delete(不用手动 free) | `m_Window`、`ExampleApp.cpp` |
| `std::make_unique` | 安全构造 unique_ptr 的工厂函数 | `ExampleApp.cpp` |
| `std::bind` + `placeholders::_1` | 把成员函数+对象绑成一个可调用对象,留一个参数位给将来传入 | `BIND_EVENT_FN` 宏、`Application.cpp` |
| lambda `[&](...){...}` | 匿名函数,`[&]` 表示按引用捕获外部变量 | `ExampleLayer.cpp` 的 Dispatch |
| 模板 `template<typename T>` | 写一份代码适用多种类型,编译器按调用自动生成 | `EventDispatcher::Dispatch<T>` |
| 宏 `#define` | 文本替换,`#x` 字符串化、`x##y` 拼接 | `EVENT_CLASS_TYPE`、`Core.h` |
| 单例 | 全程序只有一个实例,通过静态指针+静态 Get 访问 | `Application::s_Instance` |
| `enum class` | 强类型枚举(不会隐式转 int,名字不外泄) | `EventType`、`KeyCode` |
| 引用 `&` vs 指针 `*` | 引用=别名(不能为空、不能重绑);指针可空可重绑 | 几乎所有函数参数 |
| `const` | 不可变;方法后缀 `const` 表示"不改成员" | `GetName() const` |
| `inline` | 建议内联(通常定义在头文件里的短函数) | `Window.h` 的 getter |
| 命名空间 `namespace` | 避免名字冲突的"姓氏" | `GLCore::`、`GLCore::Utils::` |
| 默认参数 | `= "Layer"` 表示没传参时用这个值 | `Application` 构造、`Layer` 构造 |
| 迭代器 / 范围 for | `for (Layer* l : stack)` 遍历容器 | `Run()`、`OnEvent` |
| 预编译头 `glpch.h` | 把常用头预先编译,加速全工程编译 | `glpch.h` |

## 11. 常见困惑 FAQ

**Q: `BIND_EVENT_FN(OnEvent)` 到底在干嘛?**
A: 它展开成 `std::bind(&Application::OnEvent, this, std::placeholders::_1)`。意思是:把"`Application` 的成员函数 `OnEvent`"和"`this` 这个对象"绑成一个**可调用对象**,留一个参数位(`_1`)给将来传入的 `Event`。这样 GLFW 窗口一有事件,就能直接调这个绑好的对象,相当于"把成员函数变成普通回调函数"。这是初学者最容易卡的地方,注释里有详细拆解。

**Q: 为什么事件要从层栈"顶到底"逆序传播?**
A: 因为 overlay(如 ImGui)画在最上面,应该**优先**收到事件——你点 ImGui 面板时,不该同时触发下面的游戏逻辑。逆序 + `Handled` 就停,让"上层"有机会"吃掉"事件。

**Q: 为什么 `Window` 和 `Input` 是抽象类,还要再写 `WindowsWindow`/`WindowsInput`?**
A: 这是"平台抽象层"。引擎核心只认识抽象接口;不同操作系统(Windows/macOS/Linux)的窗口实现不同,各自写一个子类。将来要支持别的平台,加一个 `Platform/Linux/LinuxWindow` 即可,核心代码一行不用改。

**Q: `glpch.h` 是什么?为什么有个空的 `glpch.cpp`?**
A: 预编译头(Precompiled Header)。把 `<iostream>`、`<vector>` 这种几乎每个文件都 include 的标准头放进 `glpch.h`,编译器先把它编译成二进制缓存,后续文件 include 它就秒级完成,大幅加速编译。空的 `.cpp` 是为了让 premake 有个翻译单元来生成这个预编译缓存。

**Q: `GLCore.h` 和 `GLCoreUtils.h` 是干嘛的?**
A: 聚合头(umbrella header)。客户端只要 `#include <GLCore.h>` 就等于 include 了引擎的所有核心头;`GLCoreUtils.h` 则一次性带入所有工具类。省得你一个个 include。代价是编译稍慢(把一堆头都拉进来)。

**Q: 为什么顶层有两个 workspace(Sandbox 和 Examples)?**
A: 项目被重构成了"引擎 + 多个客户端"的结构。两个客户端各是一个独立的可执行程序,共用引擎库。你想研究示例就开 `OpenGL-Examples` workspace,想自己实验就开 `OpenGL-Sandbox` workspace。注意:同一个 `premake5.lua` 文件里依次定义了两个 workspace,这是 premake 的合法用法。

**Q: 我改了着色器 `.glsl` 但画面没变?**
A: 着色器是在 `OnAttach` 时加载并编译的(程序启动时)。改完着色器要**重新运行程序**才会重新加载。有些引擎支持热重载,这个项目没有。

**Q: 资产路径 `assets/shaders/...` 是相对于什么?**
A: 相对于程序运行时的**工作目录**。用 IDE/命令行跑时,工作目录通常是工程文件所在目录或可执行文件目录,具体看你怎么跑。如果报"找不到着色器文件",多半是工作目录不对。
